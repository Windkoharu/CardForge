### (4) `CardForge-过渡-档位一览.png`（2888×854，art_fade=0/6/10/16/24 五档）
- **五档几乎看不出差异**——`art_fade=0`（最左）与 `art_fade=24`（最右）的插画窗边缘肉眼看不出区别。
- 原因在代码：`_art_bleed()`（`compositor.py:781-802`）把插画 **3×3 平铺**到大画布上再模糊，外溢层用的还是插画自己的颜色（米色/金色调），而卡框本身也是米色/金色调 → **颜色相近，外溢完全被淹没**。

- 另外五张卡的 `【魔法师族／効果】` 都**比框自带的类型行低约 40px**（重影），重复验证【高-4】。

## 0. 一句话结论

**标准卡（怪兽/魔陷）的官方框基座几何精度非常高（插画窗与官方框白窗误差 ≤1.6px），但文字排版有一个会命中绝大多数卡的算法缺陷——正文被无条件横压 20%；灵摆卡则因为「官方灵摆框是一整块大白窗、渲染器只盖了三块面板」而露出 35px 白条和 13px 缝隙；罕贵覆膜是整卡平铺，没有分层工艺；渲染性能被 `draw.textlength` 的 O(n²) 调用拖垮（长文卡 2.75 s/张，占 96% 时间）。**

## 1. 架构说明

### 1.1 渲染管线分段

`render_card()`（`compositor.py:929-1114`）是一条**单函数线性管线**，15 个编号段落：

| 段 | 功能 | 入口函数 | 关键参数 / 行号 |
|---|---|---|---|
| ①②③ | **卡框基座 + 插画粘贴** | `_official_base()` `compositor.py:840` / `_procedural_base()` `compositor.py:871` | `frame_mode="official"\|"procedural"`；`T.frame_available()` 决定走哪条；官方素材缺失自动回退程序画（`:958-964`） |
| ④ | **卡名** | 内联，`:968-980` | `nx=T.sx(62)`、`name_max_w=T.sx(608)`、`nf` 从 `FONT_SIZE["name"]*SY` 逐步降到 `sy(40)` |
| ⑤ | **等级/阶级星** | `_draw_stars()` `:372` | `T.region("level_star"/"rank_star")`、`size=gh`、`step=size+sx(2)` |
| ⑥ | **右上徽记**（属性/魔陷种类） | `_draw_badge()` `:436` | `T.region("badge")`、`_ST_TYPE_KEY`、`T.ATTRIBUTE_ICON` |
| ⑦⑧⑨ | **正文**（灵摆走双框专用路径） | `_draw_pendulum_body()` `:601` / 通用单框 `:996-1045` | `T.region("text_panel"/"text_box"/"text_box_st")`、`fit_text_block()` `:337` |
| ⑧ | **类型行** | `_type_line()` `:683` | 魔陷右对齐用 `T.region("st_label")` `:1010-1017` |
| ⑨ | **效果文正文** | `fit_text_block()` + `_draw_block()` `:310` | `profile = "lore"`（通常怪）或 `"description"`；`tpad=T.sx(8)` |
| ⑩ | **ATK/DEF/LINK 数值** | `_stat_parts()` `:707` / `_fmt()` `:717` | `T.point("atk_value"/"def_value"/"link_value")`、`FONT_SIZE["atk_def"]/["link"]` |
| ⑩b | **统计分隔线** | 内联 `:1066-1071` | `T.region("stats_separator")`；灵摆改写为 `sx(130)/sx(556)` |
| ⑪ | 灵摆刻度 | 死代码 `if False:` `:1075-1089`（已并入 `_draw_pendulum_body`） | — |
| ⑫ | **连接箭头** | `_draw_link_arrows()` `:486` | `T.ARROW_DIRS` 8 方向 × on/off；`size=sx(56)`；`rel` 方位系数 `:496-498` |
| ⑬ | **外设**：版权标 / 20 周年标 | `_draw_copyright()` `:560` / `_draw_stamp20()` `:587` | `T.COPYRIGHT[(lang,color)]`、`T.STAMP["20th"]`；锚点 `sx(732), sy(1147)`，宽度 `sx(480)` |
| ⑭ | **罕贵覆膜 + 激光标** | `_draw_rarity()` `:527` / `_draw_laser()` `:543` | `T.RARE[key]`、`T.LASER[n]`、`T.region("sticker")` |
| ⑮ | 光效（UI 预览用） | 内联 `:1104-1110` | `holo=True` |
| — | **收尾降采样** | `:1112-1113` | `canvas.resize(size, LANCZOS)`；导出见 `export_card()` `:1118` |

**关键实现细节**：
- 合成画布固定 `CANVAS=(1140,1662)`（`template.py:49`），坐标基准 `REF=(813,1185)`，换算 `sx()/sy()`（`template.py:58-65`），`SX=1.402214`、`SY=1.402532`。
- 官方卡框素材原生 `1394×2031`，`_official_base` 在 `compositor.py:855-858` 直接 `frame_img.resize((1140,1662))` 铺底。
- 插画窗**不用遮罩**，矩形粘贴（`compositor.py:865-867` 注释：卡框插画窗四角均为直角）。

### 【致命-1】正文被无条件横压 20%，行数与换行点全错

- **现象**：所有效果文都以 **`scale_x = 0.80`** 渲染。实测 `c02_effect`：正文 4 行，每行渲染宽度 1073–1163px **远超可用宽 935px**（123.8% / 124.2% / 124.4% / 114.8%），被 LANCZOS 压回去。结果是**字体横向被压扁、笔画变形**，且换行点与官方不一致（官方 5 行 → 实际 4 行）。
- **影响卡种**：**全部**有正文的卡（怪兽/魔陷/灵摆），无一例外。
- **根因**：`compositor.py:337-368` `fit_text_block()` 的档位内搜索顺序错误。
  ```python
  steps = [round(1.0 - i*q, 4) for i in range(...)]   # :347 → [1.00, 0.99, ..., 0.80]
  for prof in profiles:                                # :350 先遍历字号档
      for cx in steps:                                 # :355 再遍历横压步长
          lines = wrap_text(text, f, int(max_w / cx), d)   # :356 注意 max_w/cx 放宽了可用宽
          if len(lines) <= max_lines and len(lines)*line_h <= max_h:
              return f, cx, lines, line_h              # :358 命中即返回
  ```
  在 `large` 档（`fontSize=30` → 实际 42px）：`cx=1.00` 时算得 **5 行**，`maxLines=5` 恰好命中上限；但因为 `wrap_text` 的可用宽被写成 `max_w/cx = 935/1.00 = 935`，而卡文的换行结果刚好 5 行 —— 代码继续降到 `cx=0.99`、`0.98`…… `wrap_text` 的可用宽变成 `935/0.80 = 1169`，**每行多塞 2 个字**，行数降到 4 行，于是「命中」并返回 `cx=0.80`。
  **代码把「压得越扁越容易放下」当成了优化目标，一路压到下限 0.80 才停。**
- **实测证据**（探针 5 ②）：
  ```
  档 large  size=42 lh=42.0 maxLines=5
     → 命中 横压=0.80  行数=4  占高=168/205
        L1 w=1157.0/935 (123.8%)
        L2 w=1161.0/935 (124.2%)
  ★ 若允许 横压=1.00：size=42 行数=5 可以放下！ 每行 96.6%–99.1%
  ```
- **修复建议**（小改即可，改 4 行）：
  ```python
  steps = [1.0, 0.99, ..., 0.80]        # 不变
  for prof in profiles:
      f = font(kind, size); line_h = ...
      # ① 先试完全不加压
      lines = wrap_text(text, f, max_w, d)
      if len(lines) <= max_lines and len(lines)*line_h <= max_h:
          return f, 1.0, lines, line_h
      # ② 再试横压，但只在「不横压时只差一点点」的情况下启用
      for cx in steps[1:]:
          lines = wrap_text(text, f, max_w, d)      # ← 注意：用 max_w，不是 max_w/cx
          if len(lines) <= max_lines and len(lines)*line_h <= max_h:
              return f, cx, lines, line_h
  ```
  更贴合官方的做法是**完全去掉档位内横压**（官方卡只在极端长文时压缩），只保留 `FIT_PROFILES` 的字号降档。

### 【致命-3】long-text 渲染 2.75 s/张，96% 时间花在 `draw.textlength`

- **现象**：热缓存下 `x06_longtext`（476 字）单卡 **2745.8 ms**，同条件普通卡 **207.1 ms**——**慢 13 倍**，且随文本量呈 O(n²) 增长。
- **影响**：所有长卡文卡（`x06`）+ 灵摆双文本框（调两次 `fit_text_block`）+ UI 实时预览（`preview_spec` 每次拖动都重渲）。
- **根因**：`cProfile` 打点（探针 7 ⑤）：
  ```
  2851 ms total
   2753 ms  fit_text_block            (compositor.py:337)
   2753 ms    └ wrap_text             (compositor.py:278)  × 85 次
   2681 ms        └ draw.textlength   × 40565 次
   2595 ms            └ Font.getlength
  ```
  `wrap_text()`（`:278-307`）的断行算法是**逐字符累积 + 每次 `draw.textlength(trial)` 全串重测**（`:299`）：
  ```python
  trial = cur + token
  if draw.textlength(trial, font=font_) <= max_w or not cur:   # :299 ← 每加一个字就全串量一次
  ```
  而 `fit_text_block` 会调用 `wrap_text` **85 次**（4 个字号档 × 21 个横压步长 + 末尾截断），于是 40,565 次全串测量。
- **修复建议**（小改即可，收益极大）：
  1. **给 `wrap_text` 加字符宽度缓存**——同字体下一个字符的宽度是常量：
     ```python
     _wcache: dict = {}
     def _cw(font_, ch, draw):
         key = (id(font_), ch)
         w = _wcache.get(key)
         if w is None:
             w = draw.textlength(ch, font=font_); _wcache[key] = w
         return w
     ```
     累积宽度用加法而不是全串重测 → 40,565 次降到 ~字符种数（几百次），实测可预期降到 **<100 ms**。
  2. 给 `fit_text_block` 的结果**按 (text, max_w, max_h, profile_set) 做 LRU 缓存**，UI 重复预览同一张卡时零成本。

### 【高-4】类型行与官方框自带类型行错位 37–44px，并压住文本框顶边

  ```python
  "text_box": (65.5, 897, 684, 146),
  ```
  **注意**：改完要重新跑一遍 `c01`–`c10` 目视复核，因为 `text_box` 上移会让正文整体上移 43px、可用高度不变。

- **无法表达的**：`二重`（Gemini）、`灵魂`（Spirit）、`同盟`（Union）、`卡通`（Toon）、`反转`（Flip）、`特殊召唤`（Nomi）、`超量`/`同调`×`调整`之外的组合。
- **影响**：任何需要这些类型的卡。
- **修复建议**（小改即可）：把标签表做成 `template.py` 里的数据表，加一个 `TYPE_FLAGS = {"调整":..., "二重":..., "灵魂":..., "同盟":..., "卡通":..., "反转":...}`，`_type_line` 按固定顺序拼接。

### 【中-11】`frame="token"` 的类型行退化成「效果」

- **现象**：`x14_token.png` 的类型行显示为 `【天使族／效果】`，而官方衍生物是 `【天使族／衍生物】` 或仅有名字。
- **根因**：`_FRAME_TYPETEXT`（`compositor.py:677-680`）没有 `token` 键；`_type_line` 的 `order` 字典（`:693-695`）也没有 `token`，于是 `tags = []`，race 存在时输出 `【{race}／】`——但实测输出是「效果」，说明走了 `FRAMES.get(frame, FRAMES["effect"])` 的默认路径。
- **修复建议**（小改即可）：给 `_FRAME_TYPETEXT` 和 `order` 加 `"token": "衍生物"`。

### 【中-12】20 周年标与灵摆怪兽效果框重叠 51px

- **现象**：`stamp20=True` 时印记压在灵摆怪兽效果框的文字区上。
- **实测**（探针 11 ②）：
  ```
  GEO['stamp20'] = x87-233 y1478-1596
  灵摆怪兽效果框 = y1252-1529
  → 重叠 y1478-1529 = 51px
  ```
- **影响**：灵摆卡 + `stamp20`。
- **根因**：`_draw_stamp20()` `:587-598` 使用固定 `GEO["stamp20"] = (62,1054,104,84)`，这个值是按**标准框**（文本框底 y1558）标定的，灵摆框的怪兽效果框底边更低（y1529）却与印记重叠。
- **修复建议**（小改即可）：`_draw_stamp20` 里按 `spec["frame"]` 分支，灵摆卡把印记上移到 `pendulum_panel` 左侧空白处。

### 【中-13】「出框 / Full Art」完全不支持

- **现象**：插画**永远被裁成插画窗的宽高比**（`_art_at()` `:732-743` → `crop_to_ratio()` `:251-263`），无法让插画溢出卡框；文本框也没有半透明模式。
- **量化**（探针 7 ④）：`crop_to_ratio` 对极端比例非常暴力——
  ```
  600x2400 (1:4)  → 600x600  丢弃 75.0% 像素
  2400x600 (4:1)  → 600x600  丢弃 75.0% 像素
  832x1216 (竖构图，AI 出图常见) → 832x832 丢弃 31.6%
  ```
  竖直裁切用 `y = (h-nh)*0.38`（`:262`）——**固定偏上 38%，没有主体检测**，人物经常被切掉头或脚。`x04_tallart.png` 就是活生生的例子：1:4 竖图被裁成正方形后画面完全无意义。
- **修复建议**（必须重写）：加 `spec["art_overflow"] = {top,left,right,bottom}` 或 `full_art: True`，在 `_official_base` 里把插画贴到插画窗之外，并用 `T.frame_mask()`（**已有函数，`template.py:469`，当前无人调用**）做溢出区遮罩。

### 【中-14】星带与画窗之间的暗部过重

- **现象**：等级/阶级星与插画窗之间存在一条**明显偏暗的横带**（`z_stars_effect.png` 里星下方那条深棕/黑色渐变）。真卡这里比较干净。
- **根因**：**两层暗部叠加**——
  1. 官方卡框素材自身在插画窗上方有一圈内阴影斜边；
  2. `_art_ring()`（`:765-778`）默认 `ART_RING_DEFAULT = 29.5`（813 系）= 41px，`ART_RING_ALPHA = 0.77`，向外扩张 41px。实测画窗上边外侧：`d=-3` 处渲染 36.0 vs 裸框 118.0 → **暗了 82 个亮度单位**；画窗右边 `d=+2` 处暗了 **101.7**。
  `template.py:158-170` 的注释自己也写明了：「**真卡实测只有 2–3px 的印刷柔化（跳变 34–44），不含这圈暗环；设 art_ring = 0 即回到严格按实卡**」。
- **影响**：全部卡（默认开启）。
- **修复建议**（一行）：把 `ART_RING_DEFAULT` 从 `29.5` 改为 `0` 或 `6~10`（保留轻微柔化），或把 `ART_RING_ALPHA` 从 `0.77` 降到 `0.30`。

### 【中-15】灵摆系列整体是「官方壳 + 自绘内脏」，永远达不到标准框的质感

- **现象**：官方灵摆框素材只有「上橙下绿外壳 + 一整片白窗」，**没有任何内部结构**（探针 1c / `frame_pend_lower.png` 确认：截取素材下半部是一整块纯白）。灵摆效果框、怪兽效果框、刻度、类型行、数值行**全部由 `_draw_pendulum_body` 用 `rounded_rectangle` + `_vgradient` 现画**。
- **对比证据**：*CardForge-灵摆卡-与真卡对照.png* 左（程序画）vs 右（真卡 Odd-Eyes）——真卡的灵摆框有刻度凹槽、渐变饰边、与卡框一体的斜面；程序画的是两个平面奶油色圆角矩形 + 两个菱形色块。
- **影响**：全部灵摆卡。
- **修复建议**（必须重写）：要么找一套带完整灵摆内饰的卡框素材，要么按真卡像素级重标定 `pendulum_panel` / `pendulum_monster_panel` / 刻度的几何与配色（当前 `pendulum_panel` 高 135 单位 vs 真卡 745–880=135 ✅ 对齐没问题，问题在于**绘制手法是色块而非素材**）。

### 【低-16】`GEO` 里的二元组用 `region()` 会抛异常

| 加外设（激光/版权/周年） | +5–10 ms | — |

**结论**：
- 正常卡 70–250 ms 可以接受。
- **长卡文是 13 倍退化，且完全是 `draw.textlength` 调用次数问题**（40,565 次 = 96% 时间），不是图像处理慢。
- `_official_base` 里 `frame_img.resize((1140,1662), LANCZOS)`（`:857`）把 `1394×2031` 素材降采样到 1140，**每次渲染都算一遍**——`template._img_cache` 缓存的是**原始 1394 图**，不是缩放后的。建议把缩放结果也进缓存（key 带上尺寸）。
- `_art_bleed`（`:781-802`）每次渲染都构造 `3×3 平铺的大图 + 两次 GaussianBlur`；默认 `ART_FADE_DEFAULT=0.0` 时 `b=0` 会提前返回（`:791-793`），这条路径实际不耗性能——但一旦用户开了 `art_fade`，代价会很高。

## 8. 一条正面结论（不要误伤）

标准框的**几何标定是可信的**：探针 1c 实测官方 `frame/effect.png` 白窗 `x171–1222 y375–1427` 折算到 813 系是 `x99.7–713.3 y218.8–833.2`，与 `GEO["artwork"] = (100,219,613,613)` 完全一致；按 `1140/1394` 缩放后落在画布 `l=139.8 t=306.9 w=860.3 h=861.7`，渲染器用的是 `l=140.2 t=307.2 w=859.6 h=859.8`——**误差 ≤1.6px（0.19%）**。`NOTICE.txt:40-43` 里那句「误差 0.06%，可直接互换」是**经得起复核的**。

`template.py` 顶部注释里那句「v1 的插画窗比真卡小了一半，是本轮修掉的主要缺陷」也是真的——问题不在几何，在**文字排版算法、灵摆的内饰绘制、以及罕贵的覆膜工艺**。
